# Q6.1 - AI 协作反向分析

## 选定的题目：Q4.1 评价文本结构化抽取

## 1. 我的第一个 Prompt

*以下为根据实际开发过程整理的首轮需求摘要，非逐字聊天记录。*

```text
我现在需要完成 Q4.1 评价文本结构化抽取任务。

数据集是 Olist 的 order_reviews 表，主要处理葡萄牙语差评，评分小于等于 3 分。

我的目标是构建一个完整的 Python Pipeline，将非结构化评论转换成结构化 JSON。

要求：
1. 抽取 delivery_late、wrong_product、quality_defect、
   missing_item、seller_communication、packaging、other 七类问题。
2. 输出 severity、葡萄牙语原文证据、英文翻译、
   sentiment_score、actionable_for_seller 和 confidence。
3. 总成本不超过 3 美元，处理时间不超过 40 分钟。
4. 尽可能结合 Python 规则、小模型和 DeepSeek API，
   避免所有评论都调用大模型。
5. 输出严格符合指定 JSON Schema。
6. 保留缓存、失败记录和 Token 使用统计。

请结合实际工程要求，帮助我设计和实现完整 Pipeline。
```

**为什么这样写：**

一开始我主要关注的是如何利用大模型完成葡萄牙语评论分类和信息抽取，同时受到成本和时间限制，因此希望通过规则和小模型减少 API 调用。但随着实际开发深入，我逐渐意识到，这道题的难点并不只是调用 API，而是如何设计合理的任务分流机制，以及保证抽取结果的真实性和可验证性。

---

## 2. AI 的回答

AI 最初建议采用分层处理方案：

1. 使用 Python 规则处理极短、简单的评论。
2. 使用 MiniLM 进行语义向量编码和相似度计算，识别潜在问题类别。
3. 对复杂评论调用 DeepSeek，完成结构化信息抽取。
4. 使用 SQLite 缓存 Embedding 和 LLM 结果，避免重复计算和调用。
5. 通过 JSON Schema 对模型输出进行验证，并记录 Token 消耗和失败情况。

在此基础上，我逐步完成了 Python + MiniLM Fusion 和 DeepSeek Extraction 两部分的代码整合。

---

## 3. 你迭代了几轮 Prompt？

经历了多轮迭代，主要分为以下几个阶段：

- **第一阶段：** 明确任务需求和 JSON Schema，确定问题类别、严重程度、证据原文及情感分数等字段。
- **第二阶段：** 调整 Python 规则与 MiniLM 的分流策略，避免简单评论消耗大模型资源。
- **第三阶段：** 接入 DeepSeek API，解决环境变量、API 配置和 JSON 解析等问题。
- **第四阶段：** 引入 SQLite 缓存、失败重试、Token 统计和结果审计。
- **第五阶段：** 根据实际运行结果检查输出记录数量、重复 ID、空评论、失败记录及 API 调用情况。

---

## 4. AI 的最终答案有什么错误或不足？我是怎么发现并修正的？

实际开发过程中，我发现 AI 提供的方案并不一定能够直接用于真实数据。

**问题一：没有充分区分数据处理和模型抽取。**

最初我对去重和数据处理的理解不够清晰，容易将评论去重、Review ID 去重和模型结果缓存混为一谈。后来通过检查原始数据和中间产物，明确了不同环节的处理对象和作用。

**问题二：API 调用成功不代表整个抽取流程成功。**

DeepSeek API 单独测试能够返回 HTTP 200，但正式 Pipeline 运行时仍出现空响应、JSON 解析失败和 SSL 连接异常。说明接口连通性和批量处理稳定性是两个不同的问题。

我通过查看实际响应、失败日志和 SQLite 缓存，逐步定位问题，并调整重试、缓存及错误记录机制。

**问题三：输出结果存在完整性问题。**

在检查最终 JSON 时，我发现部分记录没有正确的原始评论信息，且存在重复 Review ID。最终输出数量也不能简单等同于成功完成 LLM 抽取的数量。

因此，我进一步检查了唯一 ID、问题抽取数量、缓存记录和失败记录，避免仅凭 Pipeline 显示完成就认定任务全部成功。

**问题四：模型判断存在误分类风险。**

MiniLM 的相似度分数只是语义相似程度，并不代表分类准确率。模型可能将表达相似但实际含义不同的评论分到同一类别。因此，仍需要人工标注样本进行验证。

## 5. 如果让我再做一次同样的题，我的第一个 Prompt 会怎么写？

我会先要求 AI 明确数据处理流程、字段定义和验收标准，而不是一开始就要求生成完整代码。

具体来说，我会先提供原始数据样例、目标 JSON Schema 和任务约束，让 AI 分别设计数据清洗、规则分流、小模型判断、大模型抽取、缓存和结果验证模块。

同时明确要求：

1. 所有输出字段必须严格符合 Schema。
2. evidence_quote 必须能够在葡萄牙语原文中找到，禁止编造。
3. 区分空评论、无问题评论、API 失败和模型成功抽取但 issues 为空的情况。
4. 对每个阶段记录输入数量、输出数量及异常数量，保证数据可追溯。
5. 先使用小规模人工标注样本验证，再逐步扩大处理范围。
6. 将实际 API 调用量、Token 消耗和成本作为工程验收指标。

**我的最大收获：** AI 可以帮助我快速实现代码，但不能代替我判断数据是否正确。尤其在数据工程中，程序能够运行和结果能够被信任是两回事。真正重要的是能够通过数据检查、日志、统计和人工验证发现 AI 输出中的问题。
